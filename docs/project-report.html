PS-02 Privacy Gateway

A privacy layer that lets Indian banks, lenders and insurers use a cloud AI model on customer documents without sending it a single real name, Aadhaar, PAN or address. The gateway masks personal data on the laptop, sends only placeholders to the AI, blocks any request that would leak, and puts the real values back into the AI's answer.

Pitch

What to say

30-second version

Every bank and insurer wants to use AI to summarise loan files, KYC forms and support tickets. But those documents are full of Aadhaar numbers, PANs, names and addresses, and sending them to a cloud AI is a privacy and compliance risk. Our gateway sits in between. It finds the personal data on the laptop, swaps each value for a placeholder like <PERSON_1>, checks that nothing real is left, and only then calls the AI. When the answer comes back, it puts the real values back. The AI does its job and never sees a real identity. On our 50-document test set, 0 values leaked.

The problem

Why this needs to exist

The documents are full of identity data

Loan applications, KYC forms, insurance claims and support tickets carry names, addresses, Aadhaar, PAN, GSTIN, voter ID, passport, phone and email, often several people per document.

Cloud AI means the data leaves

Sending raw text to an external model puts customer identities on someone else's servers. India's Digital Personal Data Protection Act, 2023 expects organisations to process only the personal data a purpose needs. Summarising a document doesn't need the real Aadhaar number.

Simple redaction breaks the answer

Replacing everything with [REDACTED] confuses the AI ("which person signed?") and leaves the answer useless to staff. Values have to come back after the AI is done.

Our answer: reversible, typed masking with a hard stop

Typed placeholders (<PERSON_1>, <PERSON_2>, <PAN_1>) keep the meaning the AI needs: who is who, which ID is which. A leak guard refuses to send anything that still holds a real value. Reinsertion makes the final answer complete again, for the user only.

Components in detail

What each part does, and why

1 · Detection, rule lane: Microsoft Presidio

gateway/recognizers.py
  • 7 recognizers only: Aadhaar, PAN, GSTIN, Voter ID (EPIC), Passport, Indian phone, email. Presidio's other defaults (credit cards, IPs, dates, US IDs) are switched off so they can't raise false alarms.
  • Three kinds of evidence: the shape of the value, a built-in check (Aadhaar's Verhoeff checksum, GSTIN's state code 01–37 and structure, email's RFC 822 check, Google's phonenumbers for phones) and a keyword nearby.
  • Scoring: each candidate scores 0–1 and must reach 0.40. A keyword within six words before it adds +0.35. A checksum-valid Aadhaar scores 1.0 on its own; a passport-shaped string scores 0.10 and needs the word "passport" nearby.
  • Hinglish keywords: aadhar, adhaar, mob, matdata, elector, alongside the English ones.
  • Tightened: Presidio's loosest PAN pattern (any 10-character word with 4 digits) was removed. A backup rule masks an Aadhaar-shaped number that fails the checksum, but only when an Aadhaar keyword is right next to it, so typos and made-up numbers don't leak.

2 · Detection, AI lane: GLiNER + postal-address rule

gateway/ner.py
  • GLiNER (urchade/gliner_multi_pii-v1) is a small multilingual model built for finding personal data. It runs on the laptop's CPU, offline. We ask for person and address with 50% minimum confidence.
  • Long documents are read in 200-word windows that overlap by 30 words, so a name at a window edge is still seen whole.
  • Postal-address rule, always on: a premises word (House No., Flat, Plot, Unit…) + comma-separated parts + a 6-digit PIN code. Tuning showed GLiNER misses the "House No. 401, …, Delhi - 110017" layout, so rule and model now run together and the merge joins their spans.
  • Filters drop generic words the model sometimes tags: "Hi Team", "Technical Support", a lone "Address".
  • Fallback: if GLiNER can't load, spaCy's name finder plus the address rules take over automatically. This is tested.

3 · Merging the two lanes

gateway/merge.py
  • Longer match wins. A GSTIN contains a PAN; the whole GSTIN is kept.
  • Partial overlaps grow, never drop. If two finds half-overlap, the span widens to cover both, so no flagged character is left visible.
  • IDs beat names and addresses. A phone number inside a model-tagged address is cut out and masked as a phone; the rest stays an address.
  • Repeats are caught everywhere. Once a value is found, every other exact occurrence is masked too (whole words only, so "Ram" doesn't match "Ramesh").

4 · Masking

gateway/mask.py
  • Typed placeholders <TYPE_N>, numbered per type per request: <PERSON_1>, <PERSON_2>, <PAN_1>.
  • Same value, same placeholder, after normalising spaces, dashes and case: 5652 7833 7667, 5652-7833-7667 and 565278337667 all become <AADHAAR_1>.
  • The mapping (placeholder → real value) exists only for the request. It is never logged, stored or sent.

5 · Leak guard

gateway/leak_guard.py
  • Runs on the exact final prompt, after masking and templating, immediately before the AI call.
  • Searches for every real value, tolerant to re-spacing, dashes, dots and case. "RAHUL SHARMA" and "5652-7833-7667" are both caught, but "Ram" inside "Ramesh" is not.
  • If anything is found: the request is blocked, the AI is never called, and only the leaked types are reported, never the values.

6 · AI backends and the prompt

gateway/backends.py · gateway/prompt.py
  • GeminiBackend (Google google-genai SDK, default model set in .env; we demo on gemini-3.5-flash). Records the exact text sent. Retries overload, rate-limit and dropped-connection errors with 2 s / 4 s / 8 s waits; a bad key or bad request fails at once. A retry resends the same masked prompt.
  • MockBackend, an offline fake AI with five behaviours: echo, paraphrase (rewrites placeholders as PERSON_1, [PAN_1], <Person 1>, {X_1}), reorder, drop (deletes one placeholder), fake (invents <PERSON_9>). Free, instant and repeatable for testing.
  • Prompt tells the AI to keep every placeholder exactly as written and not to invent new ones.
  • Any model can plug in: a backend only needs a generate(prompt) method.

7 · Reinsertion

gateway/reinsert.py
  • Recognises placeholders the way AIs actually write them: <PERSON_1>, PERSON_1, [PERSON_1], {PERSON_1}, <Person 1>, <<PERSON_1>>, <Voter Id 1>.
  • Unknown placeholders (one the AI invented) are left as they are and flagged, never filled with a guess.
  • Dropped placeholders (sent but missing from the answer) are reported.
  • Uses only this request's mapping, so values from one customer can never appear in another's answer.
  • Plain words like "PAN card" or "phone 1" are not mistaken for placeholders.

8 · Audit log and API

gateway/audit.py · gateway/api.py
  • SQLite audit row per request: request ID, UTC time, backend and model, entity types with counts, the exact masked text sent, block status, leaked types, restored/dropped/unknown counts, gateway and AI timings.
  • Never stored: the mapping, the original text, the restored answer, any raw value. A blocked request stores an empty payload. A test scans every byte of the database file for raw values.
  • FastAPI: POST /process, GET /audit, GET /health, interactive docs at /docs. Input is validated (empty text and unknown modes are rejected with 422); AI failures return 502 instead of crashing.

9 · Evaluation

scripts/evaluate.py · scripts/live_gemini.py
  • Leakage: runs every document through the full pipeline, then searches what was sent for every labeled value. Target 0.
  • Detection: precision, recall and F1 per type. A find counts when type matches and spans overlap; exact-boundary matches are counted separately.
  • Reinsertion: each of the 5 Mock behaviours on every document, checked for exact restoration, correct dropped list and correct unknown flag.
  • Latency: gateway time (detect + mask + guard + reinsert), excluding the AI call.
  • Writes metrics_report.md and reports/metrics.json; the live script writes reports/gemini_run.md.

Privacy guarantees

What the design promises

Detection never leaves the laptop

Presidio, spaCy and GLiNER all run locally and offline. No personal data goes to a detection service.

The AI receives placeholders only

The Gemini backend is only ever given the finished prompt built from masked text.

A hard stop before sending

The leak guard checks the exact outgoing text. If a real value is in it, the request is blocked and nothing is sent. This is tested with a deliberately planted leak.

The mapping is short-lived

The placeholder-to-value table is created, used and thrown away inside one request. It is never logged, stored or sent.

The audit log holds no raw values

It records what was sent (already masked) and counts, for accountability. A test scans the database file byte by byte.

No cross-customer mix-ups

Reinsertion uses only the current request's mapping. Invented placeholders are never filled.

Nothing found is left visible

Overlapping detections widen instead of dropping, and repeats of a found value are masked everywhere.

Secrets stay out of Git

The API key lives in a gitignored .env file. All test data is synthetic.

Limitations

What we'd say if asked what's not solved

Being upfront about these earns more trust than claiming perfection.

The 100% scores are on the tuning set

We tuned on the same 50 documents we measured. Accuracy on new, unseen documents will be lower. Next step: a held-out set and real-world-style messy text.

Detection is the ceiling

The leak guard can only block values the detector found. A value no detector recognises would pass through. Layering (rules + model + address rule + repeats) reduces this; it can't make it zero.

Indirect identifiers stay

Employer names, job titles, rare events or a city plus a date can still hint at who someone is. We mask direct identifiers, the 9 types.

Partial name mentions

If "Rahul Sharma" is found, later "Rahul" alone is only masked if a detector finds it too. Repeat-propagation works on exact matches.

Text only, English and Hinglish in Latin script

No scanned PDFs or images yet (would need OCR first). Devanagari and other Indian scripts aren't tested.

CPU latency

About 0.4 s per document and a 12–15 s model load at startup. Fine for interactive use; bulk processing would want a GPU or batching.

Q&A preparation

32 questions judges are likely to ask

Concept

Q1Why not just use regex for everything?

Regex works for fixed formats like PAN and Aadhaar, and we use it there through Presidio, with checksums on top. Names and addresses have no fixed format, especially in Hinglish, so we need a language model (GLiNER) for those. Combining both is what got us to 100% on the test set.

Q2Why not ask the AI itself to remove personal data?

Because you'd have to send it the personal data first. The whole point is that the real values never reach the cloud model. Detection runs on the laptop.

Q3Why typed placeholders instead of [REDACTED]?

The AI needs to know who is who and which ID is which to write a useful summary. <PERSON_1> and <PERSON_2> keep two applicants apart; [REDACTED] merges them. Typed placeholders also let us put the right value back.

Q4Who is this for?

Banks, NBFCs, lenders, insurers and fintechs that want AI summaries or triage of loan files, KYC forms, claims and support tickets without exposing customer identities to a third-party model.

Q5Does this make a company DPDP-compliant?

No single tool makes a company compliant. It directly supports data minimisation: the AI processor receives only what the task needs. The audit log supports accountability by recording what was sent without storing personal data.

Detection

Q6How do you know a 12-digit number is an Aadhaar and not an order number?

Aadhaar numbers carry a Verhoeff check digit. A random 12-digit number passes only about 1 time in 10. Numbers that fail are masked only if a word like "Aadhaar" or "UID" is right next to them. Our tests confirm "order 2345 6789 0123" is not flagged.

Q7Why GLiNER and not spaCy's named-entity model?

GLiNER is trained specifically for personal data and is multilingual, so it handles Hinglish names well. It's also small enough to run offline on a laptop CPU. spaCy is kept as an automatic fallback.

Q8Why Presidio?

It's Microsoft's open-source PII framework, widely used, with ready India recognizers (Aadhaar, PAN, GSTIN, Voter ID, Passport), checksum validation and keyword-based scoring. We didn't need to reinvent that, and we tightened what was too loose.

Q9What happens with Hinglish?

14 of the 50 test documents are Hinglish and all were handled. GLiNER is multilingual, and we added Hinglish keyword spellings like "aadhar", "adhaar" and "mob".

Q10What if two detectors disagree on the same text?

The merge rules decide: longer span wins, IDs beat names and addresses, and partial overlaps grow to cover both rather than dropping one. No character any detector flagged is left visible.

Q11How do you avoid false positives like "Hi Team" being a person?

The evaluation caught exactly that. We filter spans made only of greeting and role words (team, support, sir, manager…), and lone label words like "Address". Precision went from 98.9% to 100%.

Q12Is 100% recall realistic?

It's real on this dataset, but we tuned on the same dataset, so treat it as an upper bound. The more honest headline is the method: the evaluation exposed a 52-leak gap, we fixed the root cause, and we'd validate next on a held-out set.

Masking, leak guard, reinsertion

Q13What does the leak guard actually check?

The exact final text about to be sent, after masking and templating. It looks for every real value, tolerant to spacing, dashes and case, so "5652-7833-7667" still matches "5652 7833 7667". If anything is found, the AI is never called.

Q14If detection worked, how could anything leak?

The same name written differently later (e.g. in capitals) might be missed by the masker. Our test shows exactly that case: detector found "Rahul Sharma", missed "RAHUL SHARMA", and the guard blocked the request. It's the safety net for detector mistakes.

Q15What if the AI rewrites the placeholders?

Reinsertion recognises the forms AIs actually produce: PERSON_1, [PERSON_1], {PERSON_1}, <Person 1>, <<PERSON_1>>. Our paraphrase Mock tests these on all 50 documents: 100% restored.

Q16What if the AI invents a placeholder that doesn't exist?

It's left exactly as written and flagged in unknown. We never guess a value. Tested with the fake Mock, which invents <PERSON_9>.

Q17What if the AI leaves something out?

The placeholder is listed in dropped, so the UI can show that, say, the passport number wasn't mentioned. A summary may legitimately leave details out; we report it rather than hide it.

Q18Could one customer's data appear in another's answer?

No. Each request builds its own mapping, uses it and throws it away. Reinsertion only looks up the current request's mapping, and this is tested.

Q19What if a document contains text that tries to manipulate the AI?

The worst an injected instruction can do is change the AI's wording. The AI never had the real values, so it can't reveal them. Reinsertion only fills placeholders from this request's own mapping, which holds the same user's data.

Storage, security, operations

Q20Where is the placeholder-to-value mapping kept?

Only in memory, for the length of one request. It is never written to the log, the database, disk or the network.

Q21Why log the masked payload at all?

Accountability: you can prove later exactly what was sent to the AI, and that it contained no personal data. It's already masked, so it's safe to keep. Blocked requests store nothing.

Q22How do you protect the API key?

It lives in a .env file that Git ignores, read at startup. It's never in the code, logs or repository.

Q23What if Gemini is down or overloaded?

Temporary errors (overload, rate limit, dropped connection) are retried with growing waits. Permanent errors fail at once with a clear message; the API returns 502, not a crash. In our live run one document hit an overload spike and still completed.

Q24Can it use a different AI model?

Yes. Any backend with a generate(prompt) method plugs in. Switching Gemini models is one line in .env. An on-premise model would work the same way.

Q25Why build a Mock AI?

Real AIs are slow, cost money and give different answers each time. The Mock is free, instant and repeatable, and it misbehaves on purpose in the five ways real AIs do, so we can prove reinsertion handles each one.

Performance and scale

Q26How fast is it?

Median 434 ms of gateway work per document on a laptop CPU, worst 670 ms, after a one-time 12–15 s model load. A Gemini call takes 5–7 s, so the gateway adds under 10%.

Q27How would this scale to millions of documents?

The API is stateless apart from the audit log, so it scales horizontally: more workers, each loading the models once. A GPU would cut GLiNER time sharply. SQLite would be swapped for Postgres in production.

Q28How long are the documents you can handle?

The API accepts up to 50,000 characters. GLiNER reads long texts in overlapping 200-word windows, tested on a 720-word document with the name at the very end.

Evaluation and team

Q29How was the dataset made, and is any of it real?

M3 generated it programmatically: 50 fully synthetic documents, deterministic seed, character-exact labels, validated by a script. No real person's data is in it. It covers 4 document types, Hinglish, multiple people, repeated and similar names, and documents with no PII at all.

Q30How exactly do you count a leak?

For every labeled value in every document, we search the exact text that was sent to the AI, allowing for re-spacing and case changes. Any hit is a leak. Result: 0 of 328.

Q31Phone and email aren't in the dataset. Do you handle them?

Yes: both are detected and masked (and unit-tested), but the dataset doesn't label them, so they aren't counted in the precision and recall table.

Q32How did the team split the work?

M1 + M2 built the backend: detection, masking, leak guard, reinsertion, API, audit and evaluation. M3 built the 50-document dataset and the Streamlit UI. Shared contracts agreed in the first 15 minutes let both sides work in parallel from the start.
